정규화 로그 작성 가이드

Log Normalization Format Authoring Guide

장전 서버 점검 자동화 시스템(PreCheck)이 인식하는 정규화 로그(@@@...@@@) 포맷을 정의합니다. 대상 서버 애플리케이션에서 이 포맷으로 로그를 남기면 collect 서버가 파싱하여 TB_COLLECT_LOG에 적재하고, analyze 서버가 이를 분석합니다.

적용 대상수집 대상 서버(dlprem01, pamoap01 등)의 애플리케이션 로그 출력부
파싱 주체collect/parser/LogNormalizeParser.java
저장 테이블TB_COLLECT_LOG (LOG_TYPE, LOG_ID, LOG_TIMESTAMP, LOG_CONTENT, LOG_VALUE)
01

공통 포맷 구조

Common Format
@@@[yyyy/MM/dd HH:mm:ss.SSS][입력타입][LOG_ID]|content|$값토큰$...@@@
TIMESTAMP — 로그 발생 시각 LOG_TYPE — 문구/수치/날짜/존재/정보/비교/시간 LOG_ID — 로그 식별자 CONTENT — 로그 설명(자유 텍스트) VALUE TOKEN — 타입별 값($...$)

한 라인 = 로그 1건

한 줄에 @@@가 3개 이상 나오면(=로그가 2건 이상 섞임) 파서가 해당 라인 전체를 무시합니다. 애플리케이션은 반드시 한 줄에 하나의 정규화 로그만 출력해야 합니다.

구분자는 정확히 2개

헤더([timestamp][type][id]) 뒤에는 파이프(|)가 정확히 2개 있어야 하며, content는 그 사이(1~2번째 파이프)에, tail은 두 번째 파이프 뒤에 옵니다. 파이프가 3개 이상이면 무시됩니다.

값 토큰은 content·tail 어느 쪽에 있어도 인식됩니다
파서는 content 영역과 tail 영역 양쪽 모두에서 $...$ 토큰을 찾아 합산한 뒤 타입별 개수 규칙을 검사합니다. 그래서 |home디스크|$92.7$@@@(토큰이 tail에 있음)와 |home디스크 $92.7$|@@@(토큰이 content 안에 있고 tail은 비어 있음) 둘 다 유효하고 결과도 동일합니다. 다만 tail 영역은 토큰이 아닌 문자가 섞이면 안 됩니다(토큰을 다 제거하고 남는 글자가 있으면 무시) — content 영역은 이 제약이 없어 자유 텍스트와 토큰을 섞어 써도 됩니다. 03번(값 토큰 판별 규칙)·04번(타입별 작성법) 예시가 두 위치를 모두 보여줍니다.
02

헤더 필드 규칙

Header Fields

TIMESTAMP

yyyy/MM/dd HH:mm:ss.SSS 형식 고정(밀리초 3자리 필수). 예: 2026/07/16 08:01:56.777. 형식이 다르면 파싱 실패로 라인 전체 무시.

LOG_TYPE

7종 중 하나만 허용: 문구·수치·날짜·존재·정보·비교·시간. 목록에 없는 값이면 무시됩니다(오타 주의, 공백 불가).

LOG_ID

정규식 ^[A-Za-z0-9_]{1,30}$. 영문 대소문자·숫자·언더스코어만, 최대 30자. 한글·공백·특수문자 사용 시 무시됩니다.

LOG_TYPE 7종 요약
문구 수치 날짜 존재 정보 비교 시간   — 값은 CollectConstants의 상수와 완전히 일치해야 합니다(대소문자·공백 포함).
03

값 토큰($...$) 판별 규칙

Value Token Rules

파서는 값 토큰의 내용을 보고 종류를 스스로 판별합니다. LOG_TYPE과 실제 토큰 내용이 어긋나면 무시되므로, 아래 판별 순서를 반드시 지켜야 합니다.

토큰 형태판별 기준
콜론(:) 포함시간값으로 간주 — HH:mm (2자리:2자리) 형식만 유효, 시:00~23, 분:00~59
yyyy/MM/dd 또는
yyyy-MM-dd		날짜값으로 간주 — 구분자는 토큰 하나 안에서 혼용 불가(2026/07-16 불가), 실재하는 날짜여야 함(ResolverStyle.STRICT)
그 외수치값으로 간주 — BigDecimal 파싱 가능한 정수/실수만 허용(Float/Double 사용 금지)
타입별 허용 토큰 개수는 다릅니다
수치·시간형은 값 토큰 정확히 1개, 비교형은 정확히 2개, 날짜형은 1개 이상, 문구·존재·정보형은 0개(있으면 무시)여야 합니다. 개수가 맞지 않으면 파싱 실패로 처리됩니다.
04

타입별 작성법

Format by Log Type
수치

NUMERIC — 값 토큰 1개, 시간 토큰(:) 불가

@@@[TS][수치][LOG_ID]|content|$숫자$@@@
값 토큰정확히 1개. 콜론(:)이 있으면 시간 토큰으로 오인되어 거부됨
토큰 위치content 끝(케이스 A, |home디스크|$92.7$) 또는 content 중간(케이스 B, |PROCESS 갯수 $4$ 처리중|) 어디든 가능 — 위 01번 "값 토큰은 content·tail 어느 쪽에 있어도 인식" 참조
저장LOG_VALUE(BigDecimal)에 저장, LOG_CONTENT는 토큰 제거 후 공백 정리된 문자열
용도디스크 사용률, 종목수, 접속자수, 큐 크기 등 임계치 비교 대상 수치
정상 예시 — 케이스 A(토큰이 tail에, 즉 content 끝)
@@@[2026/07/16 08:19:10.446][수치][DISK_HOME]|home디스크|$92.7$@@@ @@@[2026/07/16 08:01:56.777][수치][MBSOSI_COUNT]|주식종목수|$2078$@@@ @@@[2026/07/16 08:05:00.010][수치][CPU_LOAD]|CPU 로드율|$0.873421$@@@ @@@[2026/07/16 08:05:00.010][수치][PROC_MIN]|최소 프로세스수|$-3$@@@ ← 음수도 허용(BigDecimal 파싱 가능하면 통과)
정상 예시 — 케이스 B(토큰이 content 중간)
@@@[2026/05/28 13:01:09.555][수치][PROC_AO_TR]|ao_tr_pro_nm PROCESS 갯수 $4$ 처리중|@@@ @@@[2026/07/16 08:05:00.010][수치][DISK_HOME]|home디스크 $92.7$|@@@ ← 위 케이스 A와 결과 완전히 동일(logValue=92.7)
거부되는 예시
@@@[..][수치][DISK_HOME]|home디스크|$08:30$@@@ ← 시간 토큰(:) 포함, 거부 @@@[..][수치][DISK_HOME]|home디스크|$92.7$$91.0$@@@ ← 토큰 2개, 거부 @@@[..][수치][DISK_HOME]|home디스크|$92.7%$@@@ ← 단위 문자(%) 혼입, BigDecimal 파싱 실패로 거부
지수표기(1E10 등)는 파싱은 되지만 비권장
BigDecimal은 1.5E10 같은 과학적 표기도 파싱에 성공하지만, 로그 가독성과 analyze 임계치 비교 시 혼동을 줄 수 있어 항상 일반 십진 표기(15000000000)로 출력할 것을 권장합니다.
비교

COMPARE — 값 토큰 정확히 2개(A, B)

@@@[TS][비교][LOG_ID]|content|$A$$B$@@@
값 토큰정확히 2개. 순서상 첫 번째=A(수신/집계값), 두 번째=B(처리/기준값)로 간주되어 analyze의 ComparePolicy가 A와 B를 비교. 로그 포맷은 정책 모드와 무관하게 항상 동일($A$$B$) — 판정 방식(대칭/연산자)은 analyze 쪽 정책 설정만으로 갈림
제약두 토큰 모두 콜론(:) 불가(시간값 사용 시 거부)
용도수신 건수 vs 처리 건수, 전일 대비 금일 값 등 두 수치를 대조하는 항목(예: JUCHE_DIFF_8)
판정 결과는 analyze 정책 모드에 따라 다름(2026-08-06 신설)
로그 포맷($A$$B$ 2토큰)은 그대로지만, analyze의 PreCheck_AnalyzePolicy.conf에 등록된 비교형 정책이 대칭모드([비교][허용값%])인지 연산자모드([비교][연산자][허용오차%])인지에 따라 같은 로그도 판정 결과가 갈릴 수 있음 — 대칭모드는 정상/경고/에러 3단계, 연산자모드는 정상/에러 2단계(경고 없음). 상세 판정식은 가이드4(로그 분석 정책 가이드) 4-6절 참조.
작성 예시
@@@[2026/07/16 09:00:00.000][비교][JUCHE_DIFF_8]|수신처리비교|$1523$$1523$@@@ @@@[2026/07/16 09:00:05.000][비교][FREQ_CLUB_COUNT1]|전일대비비교|$980$$1000$@@@ @@@[2026/07/16 09:00:10.000][비교][JUCHE_DIFF_8]|수신처리비교|$1400$$1523$@@@ ← A가 B보다 많이 작음(결측 의심) @@@[2026/07/16 09:00:15.000][비교][DISK_YEST_DIFF]|전일대비|$454$$456$@@@ ← A가 B보다 살짝 작음(정상 오차 범위)
해석 (예: 대칭모드, 허용값 5%)
A=1523, B=1523 → 일치, 정상 A=980, B=1000 → 차이 20 ≤ 50(=1000×5%) → 경고 A=1400, B=1523 → 차이 123 > 76(=1523×5%) → 에러 동일 A=980,B=1000 로그를 연산자모드([>=][5])로 판정하면 컷오프=1000-50=950, A=980≥950 → 정상 (경고 없이 바로 정상)
연산자모드 방향 비교 — 정책 [비교][<=][2], 로그 $454$$456$
delta = 456×2% = 9.12 컷오프(상한) = 456+9.12 = 465.12 A=454 ≤ 465.12 → 정상
같은 로그를 [비교][>=][2]로 정책만 바꾸면
delta = 456×2% = 9.12 컷오프(하한) = 456-9.12 = 446.88 A=454 ≥ 446.88 → 정상 (연산자 방향에 따라 완화되는 쪽이 반대로 바뀔 뿐, 로그 포맷은 무관)
시간

TIME — 값 토큰 1개, 반드시 HH:mm(콜론 포함)

@@@[TS][시간][LOG_ID]|content|$HH:mm$@@@
값 토큰정확히 1개, HH:mm 형식(2자리:2자리) 고정. 콜론 없으면 수치 토큰으로 오인되어 거부
저장분(minute) 단위로 환산되어 LOG_VALUE에 저장(예: 08:07 → 487)
용도배치/수신 완료 시각이 기준 시각 이전인지 확인(예: CHEK_TIME, MOMRV_H_1)
작성 예시
@@@[2026/07/16 08:07:35.000][시간][CHEK_TIME]|처리시각|$08:07$@@@ @@@[2026/07/16 07:25:00.000][시간][MOMRV_H_1]|시세수신완료시각|$07:25$@@@ ← 경계값(정책 임계치와 정확히 일치)도 유효한 값 토큰
거부되는 예시
@@@[..][시간][CHEK_TIME]|처리시각|$487$@@@ ← 콜론 없음, 수치 토큰으로 오인되어 거부 @@@[..][시간][CHEK_TIME]|처리시각|$8:7$@@@ ← 자릿수 부족(HH:mm 아님), 거부 @@@[..][시간][CHEK_TIME]|처리시각|$25:61$@@@ ← 시:00~23, 분:00~59 범위 초과, 거부
경계값은 정책의 연산자에 달렸다
로그 값 $07:25$ 자체는 파서를 항상 통과합니다. 이 값이 정책 [시간][<=][07:25]에서는 정상, [시간][<][07:25]에서는 에러로 갈리는 것은 파싱이 아니라 analyze의 연산자 판정 문제입니다 — 가이드4(로그 분석 정책 가이드) 참조.
날짜

DATE — 값 토큰 1개 이상, yyyy/MM/dd 또는 yyyy-MM-dd

@@@[TS][날짜][LOG_ID]|content|$yyyy/MM/dd$@@@
값 토큰1개 이상, 모두 실재하는 날짜여야 함(예: 2026/02/30 같은 존재하지 않는 날짜는 거부)
판정analyze 단계에서 오늘 날짜와 문자열 비교(구분자 -는 /로 정규화 후 비교), 임계치 설정 없음
용도영업일자/배치 기준일자가 오늘 날짜와 일치하는지 확인(예: BDAY, DATE_REPORT)
작성 예시
@@@[2026/07/16 08:00:00.001][날짜][BDAY]|영업일자|$2026/07/16$@@@ @@@[2026/07/16 08:00:05.000][날짜][DATE_MULTI]|시작일종료일|$2026/07/16$$2026-07-20$@@@ ← 토큰 2개(1개 이상 허용), 각각 오늘과 비교. 구분자는 토큰마다 / 또는 - 중 하나로 통일하면 둘 다 유효
해석 / 거부
오늘(수집일) = 2026/07/16 → 일치, 정상 값이 어제 날짜면 → 불일치, 에러(일자변경 실패 감지) @@@[..][날짜][BDAY]|영업일자|$2026/02/30$@@@ ← 실재하지 않는 날짜, 거부(STRICT) @@@[..][날짜][BDAY]|영업일자|$2026/07-16$@@@ ← 토큰 하나 안에서 구분자 혼용, 거부
존재

EXIST — 값 토큰 없음, 존재 자체가 이상 신호

@@@[TS][존재][LOG_ID]|content|@@@
값 토큰없어야 함(있으면 거부)
판정analyze가 이 라인이 수집됐다는 사실만으로 항상 에러 처리(정상/경고 없음). "로그가 있으면 곧 문제"인 감시용 타입
용도비정상 잠금파일 발견, 특정 프로세스/공유메모리 이상 감지 등(예: FILE_LOCK, SHM_CHECK)
작성 예시
@@@[2026/07/16 09:30:00.100][존재][FILE_LOCK]|잠금파일 발견: order.lock|@@@ @@@[2026/07/16 09:31:12.400][존재][MEM_MBSOSI]|mbsosi 공유메모리 부존재|@@@
주의
평상시에는 이 LOG_ID로 로그 자체를 남기지 않는 것이 정상. 문제가 감지된 순간에만 애플리케이션이 이 라인을 출력.
문구

TEXT — 값 토큰 없음, content 문자열로 에러 키워드 매칭

@@@[TS][문구][LOG_ID]|content|@@@
값 토큰없어야 함
판정analyze 정책의 에러키워드 목록 중 하나라도 content에 포함되면 에러, 없으면 정상
작성 팁메시지 안에 실제 상태/결과 문자열을 그대로 남겨야 정책의 키워드 매칭(부분 포함 검사)이 동작함
작성 예시
@@@[2026/07/16 09:12:03.552][문구][SYS_MSG]|시스템 상태 점검 정상|@@@ @@@[2026/07/16 09:12:10.001][문구][DB_CONN_STATUS]|DB 접속 실패: timeout|@@@ @@@[2026/07/16 09:12:15.300][문구][PUSH_STATUS]|PUSH 전송 실패없음|@@@ ← 부분포함 매칭 함정, 아래 참조
해석 (정책: 오류,실패,error,timeout)
1번째 줄: 키워드 미포함 → 정상 2번째 줄: "실패","timeout" 포함 → 에러 3번째 줄: "실패없음"에 "실패"가 부분포함되어 → 에러 (의도는 "실패 없음"=정상이었어도 매칭됨)
키워드 매칭은 부분 문자열 포함 검사입니다
정규식이 아니라 단순 contains()이므로 "실패없음", "미실패"처럼 부정 표현 안에 에러 키워드가 그대로 들어 있으면 의도와 반대로 에러 처리됩니다. 이런 문구를 출력해야 한다면 애초에 에러 키워드와 겹치지 않는 표현(예: "PUSH 전송 정상 완료")으로 로그 문구 자체를 바꾸는 것이 안전합니다.

06

파서가 라인을 무시하는 조건

Lines the Parser Discards

LogNormalizeParser는 아래 조건 중 하나라도 걸리면 예외를 던지지 않고 해당 라인만 조용히 무시(WARN 로그만 남김)합니다. 라인 전체를 버리므로 원하는 로그가 수집 안 됐다면 이 표부터 점검합니다.

단계조건결과
1라인에 @@@ 자체가 없음정규화 로그 아님으로 조용히 통과(WARN 없음)
2시작 @@@는 있으나 종료 @@@ 없음무시 + WARN
3한 라인에 @@@가 3개 이상(로그 2건 이상 혼입)무시 + WARN
4헤더 정규식(@@@[timestamp][type][id]) 불일치무시 + WARN
5파이프(|) 누락 또는 3개 이상무시 + WARN
6tail 영역(두 번째 파이프 뒤)에 값 토큰이 아닌 문자 존재무시 + WARN
7LOG_TYPE이 7종 목록에 없음무시 + WARN
8LOG_ID가 [A-Za-z0-9_]{1,30} 불일치무시 + WARN
9timestamp 파싱 실패무시 + WARN
10타입별 값 토큰 개수/형식 불일치(위 04번 표 참조)무시 + WARN
07

작성 체크리스트 · 주의사항

Checklist & Common Mistakes
  • 파일 인코딩은 UTF-8. 한글 LOG_CONTENT가 깨지면 collect가 다른 인코딩으로 읽고 있는 것
  • LOG_ID는 영문/숫자/언더스코어만, 최대 30자 — 새 항목 추가 시 반드시 정규식으로 먼저 검증
  • 한 줄에 로그 1건만 — 여러 값을 남기려면 LOG_ID를 나눠 여러 줄로 출력
  • 수치값은 부동소수점 오차가 없는 형태로 출력(내부적으로 BigDecimal 파싱, 지수표기 1e10 등은 피할 것)
  • 같은 LOG_ID라도 서버(serverId)별로 값의 의미가 다를 수 있으므로 analyze 정책은 서버구분+LOG_ID 조합으로 따로 등록(가이드4 참조)
  • 새 LOG_ID를 추가했다면 analyze의 PreCheck_AnalyzePolicy.conf에도 등록해야 판정됨 — 미등록 시 ANALYZE_LEVEL='미분석'으로만 저장되고 SMS 통보 대상에서 제외

수치형에 콜론이 섞인 값

$08:30$처럼 콜론이 들어가면 무조건 시간 토큰으로 판별되어 수치형 검증에서 거부됩니다. 시각을 남기려면 반드시 "시간"형을 사용하세요.

content에 파이프(|) 포함

content 문자열 안에 |가 들어가면 구분자 개수가 어긋나 라인 전체가 무시됩니다. 파이프 대신 다른 구분 문자를 쓰세요.

존재형에 값 토큰을 추가

존재형은 "발생 자체가 에러"인 타입이라 값 토큰이 있으면 안 됩니다. 수치를 남기고 싶다면 수치형이나 정보형을 사용하세요.

timestamp 형식 임의 변경

yyyy-MM-dd나 밀리초 생략 등 포맷을 조금이라도 바꾸면 파싱이 실패해 라인 전체가 사라집니다. 로거 설정에서 포맷을 고정하세요.
