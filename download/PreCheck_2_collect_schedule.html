공통 포맷

Common Format
[서버ID][서버IP][수집대상파일경로][스케줄표현식]
서버ID — TB_COLLECT_LOG.SERVER_ID로 저장되는 서버 식별자 서버IP — SFTP 접속 대상 IP(local 모드에서는 미사용) 수집대상파일경로 — 절대경로, 날짜 자리표시자 사용 가능 스케줄표현식 — 배치|주기 + 요일/시각/간격

주석·빈 줄

#로 시작하는 라인과 빈 줄은 무시됩니다. 라인당 대괄호 토큰이 정확히 4개가 아니면(포맷 오류) 해당 라인은 무시되고 WARN 로그만 남습니다.

재로딩 주기

스케줄 파일은 메모리에 최대 60초(precheck.collect.scheduler.reload-interval-ms) 캐싱됩니다. 파일을 고쳐도 최대 1분 뒤에 반영됩니다(서버 재기동 불필요).

02

스케줄표현식 — 배치 vs 주기

Schedule Expression by Mode
배치

BATCH — 하루 한 번, 파일 전체를 처음부터 읽음

배치|요일|시작시각(HHmmss)
동작지정 요일의 시작시각에 단 한 번, 파일을 1번 라인부터 끝까지 전부 읽음. LAST_LINE_NUMBER를 쓰지 않으므로 "날짜 바뀌면 리셋" 개념 자체가 없음 — 실행될 때마다 항상 처음부터
크기 제한파일이 300MB(INIT_COLLECT_SIZE_LIMIT_BYTES) 이상이면 영구 제외(EXCLUDE) 등록. 큰 파일은 배치 대상으로 쓰지 말 것
적합한 경우정해진 시각에 한 번만 전체 스냅샷을 읽으면 되는 파일
[dcoodb01-주문체결][127.0.0.1][/logs/monitoring.log][배치|1-5|080000]
주기

PERIODIC — 시작~종료 사이 간격(분)마다 증분 수집(기본 동작)

주기|요일|시작시각|간격(분)|종료시각
동작직전 성공 수집의 LAST_LINE_NUMBER 다음 라인부터 파일 끝까지 증분 수집(이미 읽은 라인은 재수집 안 함)
날짜 리셋직전 성공 수집의 COLLECT_DATE가 오늘과 다르면 LAST_LINE_NUMBER를 무시하고 1번 라인부터 재수집(자정 지나면 자동 리셋)
크기 제한한 번에 50MB(PART_COLLECT_SIZE_LIMIT_BYTES) 이상 증가하면 영구 제외 등록
전제조건파일 끝에만 로그가 추가되는(append-only) 환경. 중간 라인 삭제/복원 시 누락·중복 재수집 위험(아래 04 주의사항 참조)
[dlprem01-테스트개발][127.0.0.1][/logs/dlprem01.yyyymmdd.log][주기|*|080000|1|235959] → 매일(*), 08:00:00부터 23:59:59까지 1분 간격으로 증분 수집
03

파일경로 자리표시자

File Path Placeholders

로그 파일이 날짜별로 나뉘어 쌓이는 운영 환경을 위해 파일경로 안에 특수 토큰을 쓸 수 있습니다. 매 수집 시각의 수집 날짜 기준으로 치환됩니다.

토큰치환값예시
yyyymmdd수집 날짜 전체(yyyyMMdd)check.yyyymmdd → check.20260716
mmdd수집 날짜의 월/일(MMdd, 연도 구분 없음)check.mmdd → check.0716
$수집 날짜의 요일 숫자(0=일 ~ 6=토)sys0$.log → (월요일) sys01.log
경로 끝의 +날짜 리셋 비활성화(주기 수집 한정) — 실제 경로에서는 제거됨check.log+ → 자정 넘어도 LAST_LINE_NUMBER 이어서 사용
치환 순서 주의
yyyymmdd가 mmdd를 부분 문자열로 포함하므로, 파서는 반드시 yyyymmdd를 먼저 치환한 뒤 남은 mmdd를 치환합니다(순서를 바꾸면 결과가 깨짐 — 직접 정규식으로 구현할 때 참고).
04

운영자 설정 가이드 — 우리 로그는 어떤 옵션?

Operator Decision Guide
Q1. 로그 파일이 매일 새 파일로 생성되는가? (예: app.20260716.log)
YES → 경로에 yyyymmdd 사용: /logs/app.yyyymmdd.log  /  NO → 경로 그대로: /logs/app.log
Q2. (Q1=NO인 경우) 그 파일은 자정이 지나도 계속 같은 파일에 이어 쓰이는가?
YES → 경로 끝에 +: /logs/app.log+(날짜 바뀌어도 리셋 안 함)  /  NO → 그대로 둠(날짜 바뀌면 자동 리셋, 기본 동작)
Q3. 수집 주기 없이 정해진 시각에 한 번만 전체를 읽으면 되는가?
YES → 배치 (파일 300MB 미만 권장)  /  NO → 주기
"주기" 수집은 내용이 아니라 라인 수만 본다
매 수집마다 LAST_LINE_NUMBER 다음 라인부터 "그 위치에 있는 내용"을 읽을 뿐, 실제로 새로 추가된 로그인지는 확인하지 않습니다. 파일 중간/앞부분 라인이 삭제됐다가 다시 채워지면 이미 수집한 것으로 간주되어 영구히 누락될 수 있고, 반대로 파일이 과거 상태로 복원되면 중복 재수집될 수 있습니다. 이 정책은 "파일 끝에만 추가되는(append-only)" 환경을 전제로 합니다.
05

스케줄러 실행 판정

Scheduler Execution Logic
항목동작
폴링 주기@Scheduled(fixedDelay) 1초(precheck.collect.scheduler.fixed-delay-ms)마다 스케줄 목록을 검사
요일 판정*(매일), 단일 숫자(0=일~6=토), 범위(1-5=평일) 지원. 콤마·공백 구분 다중 지정은 미지원
중복 실행 방지배치는 serverId+ip+path+schedule 키로 "오늘 이미 실행했는지" 기록, 주기는 "이번 간격 구간(runIndex)에 이미 실행했는지" 기록 — 폴링 주기(1초)가 실행 판정 폭(2초)보다 짧아 중복 트리거되는 것을 방지
SFTP 계정 검증local 모드가 아닌데 전역 계정도, 서버별 override 계정(PreCheck_CollectServer_Auth.conf)도 없으면 해당 스케줄 실행을 건너뛰고 WARN
06

작성 체크리스트 · 주의사항

Checklist & Common Mistakes
  • 한 줄에 대괄호 토큰 4개(서버ID/서버IP/파일경로/스케줄표현식) — 하나라도 비어있으면 라인 전체 무시
  • 시작시각·종료시각은 HHmmss 6자리 고정(예: 080000), 시작시각 ≥ 종료시각이면 무효
  • 간격(분)은 1 이상의 정수만 허용
  • 같은 파일을 여러 스케줄 라인에 중복 등록하지 말 것 — 두 스케줄이 서로 다른 시점에 같은 파일을 읽으면 LAST_LINE_NUMBER 경합 발생 가능
  • 파일 경로는 절대경로 권장(상대경로는 애플리케이션 실행 위치에 따라 달라짐)

큰 파일을 배치로 등록

배치는 매번 파일 전체를 처음부터 읽으므로, 300MB에 근접한 파일을 배치로 등록하면 곧 영구 제외(EXCLUDE)됩니다. 큰 파일은 주기로 전환하세요.

yyyymmdd 파일에 + 접미사 오용

+는 "주기"에서만 의미가 있습니다. 매일 새 파일이 생기는 yyyymmdd 경로에 실수로 붙이면 자정 리셋 의도와 충돌할 수 있으니 Q1/Q2 순서대로 판단하세요.

스케줄 수정 후 즉시 반영 기대

스케줄 파일은 최대 60초 캐싱됩니다. 수정 직후 바로 실행되지 않아도 정상이며, 최대 1분까지 기다려야 합니다.

요일 표현에 콤마 사용

1,3,5 같은 콤마 구분은 지원하지 않습니다. 특정 요일 조합이 필요하면 별도 라인으로 나누거나 범위(1-5)를 활용하세요.
