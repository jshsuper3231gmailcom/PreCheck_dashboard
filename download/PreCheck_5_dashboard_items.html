Dashboard 확정항목 적용 가이드

Applying Confirmed Info-Data Items via application.yml

화면정의서(0-4. 정보성 데이터 서버+LOG_ID 매핑표)에서 "확정"된 카드 항목을 실제 대시보드 화면에 반영하는 절차입니다. 1차 버전은 관리자 UI로 항목을 관리하지 않고 yml 설정 파일로 관리합니다.

설정 위치dashboard/src/main/resources/application.yml → precheck.info-data
바인딩 클래스dashboard/config/InfoDataConfig.java (@ConfigurationProperties(prefix="precheck"))
소비 주체DashboardController, DashboardService
01

yml 항목 구조

info-data Item Structure

한 항목은 이름·서버구분·LOG_ID 3개 필드로 구성됩니다. 같은 LOG_ID라도 서버구분이 다르면 업무 의미가 다를 수 있어 조합 단위로 관리합니다.

precheck:
  info-data:
    - name: 주식종목수
      server-id: dlprem01-테스트개발
      log-id: MBSOSI_COUNT
    - name: HTS최대동시접속
      server-id: pmaster2-마스터
      log-id: HTS_MAX_CONN

name

화면에 표시되는 한글 라벨. 자유 텍스트이며 시스템 동작에 영향 없음.

server-id / log-id

collect·analyze 스케줄의 서버ID, 정규화 로그의 LOG_ID와 철자까지 정확히 일치해야 함. 오탈자가 있으면 조회 결과가 항상 "데이터 없음"으로 표시됨.

02

yml 등록만으로 반영되는 범위

What yml Alone Covers

가장 흔한 실수는 "yml에 추가했는데 그래프에 안 나온다"입니다. 화면 영역별로 반영 방식이 다릅니다.

화면 영역반영 방식추가 작업
3번 영역 — 정보성 중요 데이터 카드 yml만으로 자동 getAllInfoData()가 infoData 목록 전체를 그대로 순회·조회하므로 추가 코드 수정 불필요
5번 영역 — 종목수/접속자수 히스토리 그래프 yml + 코드 수정 DashboardService.getHistoryData()의 stock/overseas/conn 그룹별 LOG_ID Set.of(...)가 하드코딩 — 신규 LOG_ID를 그룹에 넣으려면 자바 코드도 수정
10번 영역 — History 페이지(월별 시계열) yml + 코드 수정 getAllGroupedHistory()의 stock/overseas/service/conn 4개 그룹 Set.of(...)도 별도로 하드코딩 — 5번 영역과 별개 위치이므로 두 곳 모두 수정 필요
6번 영역 — 서버별 리소스 도넛차트 yml 무관 서버 목록은 TB_ANALYZE_HISTORY에서 오늘 분석된 SERVER_ID를 동적 조회. 해당 서버가 DISK_HOME LOG_ID를 수집·분석하면 자동 표시(코드/yml 수정 불필요)
카드엔 보이는데 그래프엔 안 보이는 이유
새 항목을 precheck.info-data에만 추가하면 3번 카드에는 즉시 나타나지만, 5번/10번 그래프에 포함되려면 DashboardService.java 안의 해당 그룹 Set.of("MBSOSI_COUNT", ...) 리터럴에 LOG_ID를 직접 추가해야 합니다. 두 위치(getHistoryData, getAllGroupedHistory)를 모두 확인하세요.
03

신규 확정항목 적용 절차

Step-by-Step Procedure
1화면정의서 0-4. 정보성 데이터 서버+LOG_ID 매핑표에서 표시명·서버구분·LOG_ID를 담당자와 확정
"(확정 필요)" 표기가 남아있는 항목은 운영 투입 전 반드시 확정
↓
2collect 스케줄(가이드2)·analyze 스케줄(가이드3)에 해당 서버구분이 이미 등록돼 있는지 확인
신규 서버라면 두 conf 모두에 먼저 등록 — 안 그러면 로그 자체가 안 쌓임
↓
3analyze 정책(가이드4)에 해당 LOG_ID 정책이 등록돼 있는지 확인
미등록이면 카드에 "미분석"으로 표시되고 값 판정이 되지 않음(수집 자체는 됨)
↓
4application.yml(또는 프로파일별 yml)의 precheck.info-data에 항목 추가
3개 프로파일(공통/test/prod) 중 실제 반영해야 할 파일이 어디인지 04번 참고
↓
5그래프(5번/10번)에도 표시하려면 DashboardService.java의 해당 그룹 Set.of(...) 2곳에 LOG_ID 추가
기존 4개 그룹(종목/해외/서비스/접속자) 중 하나에 속하지 않는 완전히 새로운 성격의 데이터라면 그룹 자체를 신설(코드 변경 범위 넓음, 별도 검토 필요)
↓
6dashboard 서버 재기동
@ConfigurationProperties 바인딩과 DashboardService.init() 모두 기동 시점에 고정되므로 무중단 반영 불가
04

프로파일별 yml 적용 위치

Which yml File to Edit
파일역할info-data
application.yml공통 설정 + 로컬/기본 precheck.info-data 전체 목록정의됨(로컬 테스트용 서버·LOG_ID)
application-test.yml로컬 PostgreSQL datasource만 정의없음 — application.yml 값을 그대로 사용
application-prod.yml운영 PostgreSQL datasource + 스케줄 conf 경로만 정의없음 — application.yml 값을 그대로 사용
운영 목록을 로컬과 다르게 가져가려면
Spring의 YAML 리스트 프로퍼티는 프로파일 간에 병합되지 않고 통째로 교체됩니다. 운영에서 다른 서버·LOG_ID 구성을 쓰려면 application-prod.yml에 precheck.info-data 전체 목록을 새로 작성해야 하며, 항목 일부만 얹는 방식은 동작하지 않습니다.
05

체크리스트 · 주의사항

Checklist & Common Mistakes

server-id 오탈자

server-id는 한글이 섞인 문자열(예: dlprem01-테스트개발)이라 공백·오타가 나기 쉽습니다. collect/analyze conf의 값과 문자 단위로 비교하세요.

그룹 Set.of 누락

yml에만 추가하고 DashboardService.java의 그룹 상수를 안 고치면 카드에는 값이 뜨는데 히스토리 그래프에는 영영 나타나지 않아 "반영이 안 됐다"고 오인하기 쉽습니다.

정책 미등록 상태로 배포

analyze 정책 없이 yml만 먼저 배포하면 카드에 "미분석"만 표시됩니다. 3~4단계(스케줄·정책 확인)를 yml 등록보다 먼저 끝내세요.

재기동 없이 반영 기대

yml과 DashboardService.init() 캐시 모두 기동 시점에만 읽습니다. 파일만 바꾸고 재기동을 건너뛰면 이전 목록이 계속 보입니다.
